The smallest anonymised dataset that lets AviOS move prediction precision from target to observed

COMPANION TO: FLEET MRO SIMULATOR SPEC   Status: pilot-engagement spec  ·  Audience: first pilot operator (and your own negotiating position)

1. Why This Document Exists

The simulator hardens the platform and pre-trains the models, but it cannot produce a defensible accuracy number — synthetic accuracy proves the simulator, not the product. One operator's historical maintenance data is the critical path to an observed precision figure. This spec defines the smallest extract that gets there, so the ask is a one-day export job for the operator's MIS admin, not a data-integration project their IT department will veto.

Design principle: every field requested must either (a) feed fine-tuning, or (b) feed the validation protocol in §6. Anything that does neither is out — a smaller ask clears legal review faster than a better-argued big one.

History≥3 years, contiguous, ending as recently as possibleNeeds ≥2 years to train + 1 full year held out (§6); seasonality requires whole years

4. The Extract — Five Tables

Everything below is a standard export from AMOS, TRAX, or OASES. CSV or Parquet; one file per table; UTF-8; a data dictionary sheet listing any operator-specific codes.

4.1 Fleet & Utilisation REQUIRED

One row per tail per month: tail_token · aircraft_type · series · month · flight_hours · flight_cycles. Anchors every model to exposure — failures per hour, not raw counts.

4.2 Maintenance Events REQUIRED

Work orders / task cards: event_id · tail_token · ata_chapter · event_type (scheduled | unscheduled | AOG) · start_ts · end_ts · description_scrubbed · parts_consumed. Maps 1:1 to the AviOS MaintenanceEvent entity.

4.3 Component Removals & Installs REQUIRED

serial_token · pn_family · ata_chapter · position · tail_token · removal_ts · removal_reason (failed | scheduled | convenience) · tsn · csn. This table is the label source: unscheduled removals with reason "failed" are the positive class the models must predict. Maps to the AviOS Component entity.

4.4 Defects / PIREPs / MEL Items REQUIRED

defect_id · tail_token · ata_chapter · reported_ts · mel_category · symptom_text_scrubbed · resolved_by_event_id. The leading-indicator stream — recurring defects preceding a removal are exactly the pattern worth learning. Maps to the AviOS Defect entity.

4.5 Optional Boosters NICE-TO-HAVE

  • Engine trend-monitoring summaries (EGT margin, vibration trend per flight or per week) — the strongest single booster for engine-chapter precision
  • Technical delay/cancellation codes — ties predictions to the cost story
  • AOG log with resolution timeline — calibrates the simulator's repair-queue DES against reality
Explicitly NOT requested: raw full-flight QAR/FDR streams (huge, sensitive, unnecessary for this validation), crew or passenger data of any kind, commercial/financial data, safety-report (ASR/SMS) narratives. Saying this in the first meeting shortens legal review by weeks.

5. Anonymisation Rules — Privacy That Preserves Trainability

FieldRuleWhat it preserves
Tail numbersConsistent pseudonym (AC-001…), same token everywherePer-aircraft history threads intact
Part serialsConsistent hash-token per serialComponent life-tracking across removals/installs
Part numbersKeep family/ATA; hash exact PN consistentlyInterchangeability groups without exposing vendor pricing tells
DatesSingle fleet-wide constant offset (e.g. −7 to −90 days), same for all tablesAll intervals, sequences and seasonality — the actual signal
Free textStrip names, employee IDs, airport codes; keep symptom vocabulary"recurring EGT overtemp on climb" survives; who wrote it doesn't
Operator identityNo IATA/ICAO codes, no station identifiers in any fieldExtract is unattributable if leaked
One rule that matters more than the rest: pseudonyms must be consistent across all five tables. A fresh token per table destroys the joins and with them the entire training value. The provided anonymisation script enforces this with a single mapping file that never leaves the operator.

6. Validation Protocol — How the Number Gets Produced

  • Split: temporal, never random — train on years 1 to N−1, hold out the final full year. No event, defect, or removal from the holdout year touches training. Random splits leak future into past and inflate every metric; a sophisticated buyer will ask exactly this question.
  • Task: for each component/system in scope, predict an unscheduled failure-driven removal within a 30-day horizon.
  • Metrics reported: precision per alert · recall of actual failures · median advance warning (days) · false alerts per tail-month · all versus the baseline of the existing MSG-3 schedule alone.
  • Output: a validation report stating observed figures with confidence intervals. From that day forward, marketing claims cite observed precision — the target number retires.
# Acceptance gate for citing a chapter publicly
chapter_reportable = (
    unscheduled_removals_in_holdout >= 10 and
    precision_ci_width <= 0.15 and
    recall >= baseline_msg3_recall          # must beat the schedule
)

7. Handling Terms (Offer These Before Being Asked)

  • NDA + Data Processing Agreement before any transfer; encrypted transfer; processing in an isolated single-tenant environment (their VPC if preferred).
  • No third-party access, no co-mingling with other operators' data, no use beyond fine-tuning and this validation.
  • Deletion on request and automatically at engagement end; deletion certificate provided.
  • The operator reviews the validation report and approves any external citation of results — including anonymous ones — before first use.

8. What the Operator Gets

  • Fleet reliability insight report: their own top recurring-defect chains, worst-actor tails, and removal-driver ranking — genuinely useful even if they never buy.
  • First-pilot pricing locked for a defined term.
  • Named (or anonymous, their choice) position as the validation fleet in future material.
